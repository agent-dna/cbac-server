## Confidence key

- **DETERMINISTIC** — decided by plain Python (a strip(), an `if user_intent:`,
  a keyword-substring match), not by any model. If your real run disagrees
  with a DETERMINISTIC row, suspect the test setup, not the pipeline.
- **HIGH** — the action name/keyword is a near-exact lexical match to a
  policy term, where semantic models are usually reliable.
- **MEDIUM** — plausible either way; a reasonable guess, not a confident one.
- **LOW** — genuinely uncertain. These are the cases most worth reading
  closely in your real report — I'm as curious as you are what they do.

## Summary of what I'd bet on if forced to guess

If I had to guess a headline number: I'd expect somewhere between 4 and 9 of
the 40 flagged rows in the real report, concentrated in NEG, LANG, BUN, HED,
LEN, and POLICY-CATCHALL/VAGUE — the categories above marked LOW confidence.
The BND/NUM quantity-blindness cases (BND-02/03, NUM-01) I'd bet on
confirming almost certainly, since they don't depend on subtle model
behavior — they depend on the pipeline having literally no numeric
reasoning at all, which is true by construction, not by chance.

## Two fixture problems worth fixing before you run this

Building this expected-results table forced me to trace `_collect_text`'s
recursion depth by hand, and I found two cases that don't actually test what
their `hypothesis` claims:

1. **TYPE-04** — the nesting only reaches depth 4 (`nested → deeper →
   even_deeper → deepest`), but the depth cutoff in `_collect_text` is
   `_depth > 6`. The forbidden text at the bottom is never actually dropped
   — it's well within the visible range. This case currently just retests
   "does delete_invoice deny," not "does content past the depth cutoff
   disappear." To really test the cutoff, the nesting needs 3+ more levels.

2. **DIL-01** — the padding text is in a separate `context` field from
   `action: delete_invoice`. Since `_intended_action_text` flattens every
   dict value into the same string, the padding will surround the verb, but
   the verb itself stays a clean, undiluted token — this is a softer test of
   dilution than putting the forbidden verb itself deep inside the padding
   text. Worth a second, harsher variant where the verb is paraphrased
   *inside* the padding rather than kept as its own clean field, if you want
   a real stress test of this category.

Neither is wrong exactly — they'll still produce a valid result — but
neither will tell you what the category name promises. Want me to fix these
two in `intents.yaml` before you run it, or run it as-is first and treat
these as a known limitation to patch in a second pass?
